# FlashGenerate 服务端

面向部署人员。前端仍然放在静态托管上，这一份是它背后的服务：持有接口凭据、
调度生成任务、管理账号与额度、保存生成结果。

## 为什么需要它

第一版没有服务端，接口凭据存在每位使用者自己的浏览器里。这个结构下有两件事做不到：

**额度控制。** 凭据发到外部使用者的浏览器里，对方能从开发者工具取走，
之后绕开这套工具直接调平台。写在前端的额度限制拦不住任何人。

**多人同时使用。** 平台规定「重新获取凭证后旧凭证立即失效」，
所以同一套凭据同一时间只能一个人在用，第二个人打开就把第一个人挤下线。

两件事都只有一个解法：凭据交由服务端统一持有，所有平台调用经服务端转发。

## 需要准备的东西

**Postgres 14 以上。** 托管的即可，Neon、Supabase、阿里云 RDS 都行。

**一个 S3 兼容的对象存储。** Cloudflare R2、阿里云 OSS、MinIO 都可以。
桶必须是私有的——生成结果一律通过限时签名地址下发，不存在长期有效的公开链接。

**一台能常驻运行的机器。** Render、Railway、Fly、任何一台云服务器都行。
不要用 Serverless：任务需要每几秒轮询一次平台，而免费档的定时触发大多一天只跑一次。

## 配置

复制 `.env.example` 为 `.env` 并填写：

| 变量 | 说明 |
| --- | --- |
| `DATABASE_URL` | Postgres 连接串，托管库一般要求 `?sslmode=require` |
| `SESSION_SECRET` | 一串长随机值。换掉它等于让所有人重新登录 |
| `CORS_ORIGINS` | 允许访问的前端地址，逗号分隔 |
| `S3_ENDPOINT` `S3_BUCKET` `S3_ACCESS_KEY_ID` `S3_SECRET_ACCESS_KEY` | 对象存储 |
| `S3_SIGNED_URL_TTL` | 下发的签名地址有效期，秒，默认 900 |
| `BOOTSTRAP_ADMIN_EMAIL` `BOOTSTRAP_ADMIN_PASSWORD` | 首次启动创建的管理员，登录后必须改密码 |

**平台的 app_id 和 secret_key 不写在这里。** 它们在管理后台的「供应商」页填，
只存数据库。环境变量会出现在部署平台的界面和日志里，凭据不该出现在那些地方。

## 启动

```bash
npm install
npm start
```

启动时自动执行数据库迁移和初始化，不需要额外的命令。重复启动是安全的。

开发时用 `npm run dev`，改代码自动重启。

## 对象存储怎么配

桶建好之后确认两件事：

**桶是私有的。** 公开读的桶意味着任何人拿到地址就能访问，
客户之间的隔离在存储这一层就漏了。

**跨域允许前端的域名。** 浏览器要直接从签名地址加载图片和视频，
跨域规则里放行前端域名的 GET 即可，不需要放行写操作。

R2 的跨域配置在存储桶设置的 CORS Policy；阿里云 OSS 在「权限管理 → 跨域设置」。

## 上线后要做的事

1. 用 `BOOTSTRAP_ADMIN_EMAIL` 登录，按提示改掉初始密码
2. 进「供应商」页填 app_id 和 secret_key，点保存并测试连接
3. 同一页按实际套餐调整各能力的并发数
4. 在「客户账号」页建客户，设初始额度，把临时密码发给对方

## 计价怎么改

客户看到的是统一点数，平台扣的是蝉豆或魔力。两者的换算表在 `cost_rules` 表里。

这么设计是因为平台有两种货币、不同能力扣的不一样，以后换供应商单位又会变。
如果客户额度直接用平台货币来设，换供应商那天所有客户的额度全部作废。
改价只改换算表，客户已设的额度不受影响。

## 接第二家供应商

在 `src/providers/` 下新建一个目录，实现 `types.ts` 里的 `Provider` 接口，
在文件末尾 `registerProvider()` 注册，再往 `providers` 和 `cost_rules` 表插数据。

账号、权限、任务调度、额度、资料库和前端主体逻辑都不需要改。

有一条规矩要守住：**供应商的原始状态和错误码不要往上透**。
一旦透上去，调度层迟早会写 `if (provider === 'xxx')`，抽象层就名存实亡了。
状态和错误必须在适配器里归一成 `TaskStatus` 和 `ErrorCode`，
原始响应只作为 `raw` 挂着供排查，任何调度逻辑都不许读它。

## 额度与平台账单的关系

系统里的额度和平台余额不可能完全实时一致：任务是异步的，失败要退还，
平台扣费的时点也不完全可控。

这两个数是分开的：**系统里的是预算控制，平台余额是事实。**
服务端每十分钟拉一次平台余额存进 `provider_balances`，
管理后台的供应商页能看到，余额偏低会在日志里告警。

不要按「两边分毫不差」去对账，那做不到。

## 几个容易踩的地方

**平台的 HTTP 状态码恒为 200**，成功与否看响应体里的 `code`。
路径写错时才会拿到真正的 404，那种情况另算。

**`expire_in` 是过期时间戳（10 位秒），不是剩余秒数。**
当成剩余秒数会算出 1970 年，于是每次调用都判定过期、每次都重新取，
而每次重新取又会把上一个凭证踢掉。

**错误码 400 和 50000 都是平台的兜底码**，光看码判断不出真实原因，必须读 `msg`。
50000 尤其容易误判：官方释义写的是「系统内部错误」，
实际上「引用的音色/数字人/文件不存在」返回的也是它。

**账本的幂等靠 `ON CONFLICT DO NOTHING`，不要改成 catch 唯一约束错误。**
Postgres 里语句一报错整个事务就中止，catch 掉也救不回来，
后面那条无辜的语句会以「当前事务被终止」失败，很难往回查。
